# Canvas preview extensions — installable file viewers in sandboxed iframes

> API: [dev/api.md → Canvas Preview Extensions](../dev/api.md#canvas-preview-extensions). WS frames `extension:changed` / `updates:changed`: [ws.md](ws.md#other-server--client-messages). User-visible behavior: [requirements/editor.md](../requirements/editor.md). Code: `packages/core/src/protocol/extension-{types,frames}.ts`, `packages/server/src/extensions/{registry,watcher,install,state}.ts` + `routes/extensions.ts` + `middleware/auth.ts` (scoped token), `PUT /files/raw` in `routes/files.ts`, `routes/transcribe-ws.ts` (transcription proxy) + `settings-schema.ts` `extensionSections()`, `packages/admin/src/features/editor/previews/{registry,extension-host,extension-host-logic,extension-token}.ts(x)`, `packages/admin/src/features/workspace/extension-activity-{panel,logic}.ts(x)` (activity-bar pages + the shared file-less `ExtensionPageFrame`), `packages/admin/src/features/chat/extension-chatbar-{control,logic}.ts(x)` (chat-bar panels), `previews/extension-icon.tsx` (mask icon), `packages/server/src/updates/` + `routes/updates.ts` (update checks, see [Updates](#updates-updatejson)), `packages/admin/src/features/settings/{extensions-view,core-update}.tsx`, `packages/server/templates/skills/extension/`, `packages/server/src/agents/skill-sources.ts` (extension-shipped skills).

## Problem

The admin editor's preview set was compile-time: eight plugins registered in `previews/plugins/index.ts`, and every new file type (GLB, drawio, …) meant editing admin source, re-bundling and cutting a release — while each viewer's weight (model-viewer + three ≈ 1 MB) landed in every user's bundle. Extensions turn a viewer into **a static directory with an HTML entry** that the admin loads in an iframe and feeds file bytes over `postMessage`. Install = drop the directory into `~/.halo/global/extensions/<id>/`; no server restart, no page reload, no admin release.

## Directory is the install

```
~/.halo/global/extensions/
├── glb/                       # dir name == manifest.id
│   ├── halo-extension.json
│   ├── index.html             # manifest.entry
│   └── …                      # js / wasm / decoders / LICENSE
└── .tmp-unpack-a1b2c3/        # in-flight install (dot-prefixed → scanner skips it)
```

- Valid manifest present = installed; directory gone = uninstalled. No db table, no registry file — the filesystem is the truth (same model as global skills). `init.ts` only `mkdir -p`s the root; no extension is preinstalled.
- **The server scanner is the only validator.** Whoever puts a directory there (admin zip upload, `ext.sh`, manual `cp -r`) gets the same verdict. A directory that fails validation is still **listed** as `{ id, error }` so the admin shows "installed but broken" (red row, removable) rather than "not installed".
- Ids are directory names *and* URL segments: `^[a-z0-9][a-z0-9_-]{0,63}$` (`registry.ts` `ID_RE`, deliberately tighter than the session-id `isSafeIdSegment`; `ext.sh` carries a copy — keep in sync).

### Manifest (`halo-extension.json`)

| Field | Req | Rule |
|---|---|---|
| `id` | ✓ | `ID_RE`; **must equal the directory name** (`id mismatch` otherwise) |
| `name` | ✓ | ≤ 64 chars; shown in the open-with menu and Settings → Extensions |
| `version` | ✓ | semver `x.y.z[-pre]`; part of the asset URL. Install compares nothing (same id = replace); the [update check](#updates-updatejson) compares it with `semver.gt` against update.json |
| `extensions` | ✓ | array, each `^\.[a-z0-9]+$` (dot, lowercase); matched against the lowercased file ext. Non-empty (`extensions must be a non-empty array`) unless the manifest declares `activity` or `chatbar`, where `[]` = opens no files; the key stays required either way (`ext.sh`'s pre-check demands it) — with `activity` / `chatbar`, a non-array is `extensions must be an array (empty is fine with activity or chatbar)` |
| `entry` | ✓ | relative HTML path, no leading `/`, no `..`; file must exist |
| `priority` | – | `default` (default; opens the file directly) \| `option` (open-with menu only) |
| `capabilities` | – | `"save"` \| `"media"` (iframe gets `allow="microphone; display-capture; clipboard-write"`) \| `"transcribe"` (may open the server's [transcription proxy](#streaming-transcription-proxy)) \| `"fs-read"` (read-only `fs` over the workspace and the whole machine + the host file picker, bundle or not — see [Scoped file access and the picker](#scoped-file-access-and-the-picker-fs-read)) \| `"stt-local"` (may open the server's `/api/stt/stream` WS for on-device speech-to-text — see [stt-local.md](stt-local.md)); **unknown value = manifest error** (reject rather than let the host silently drop a declared capability) |
| `bundle` | – | boolean, default `false`; `true` = every suffix names a **directory** (see [Bundle extensions](#bundle-extensions)). Non-boolean, or `true` together with `save` (`bundle extensions cannot declare save`) = manifest error |
| `platforms` | – | non-empty array of `web` \| `desktop-mac` \| `desktop-win` \| `desktop-linux` (deduped); omitted = everywhere. Empty / unknown value = manifest error |
| `settings` | – | `{ params?: [field…], secrets?: [field…] }`, field = `{ key, description?, description_zh?, default?, type?, options? }` (skill `config.yaml` format). Validated **strictly** (a skill's config.yaml is parsed leniently): `key` `^[a-z][a-z0-9_]{0,63}$`, unique across both lists, `type` ∈ string\|int\|float\|boolean\|enum (enum needs `options`), scalar `default` stringified; anything else = manifest error. `ExtensionInfo.settings` carries the declarations, never values. See [Extension settings](#extension-settings) |
| `activity` | – | `{ icon?, title?, title_zh?, description?, description_zh?, order? }` = one admin activity-bar button (see [Activity-bar entries](#activity-bar-entries)). Checked after `description`, before `extensions`: non-object → `activity must be an object`; `icon` relative `.svg` / `.png` (no leading `/`, no `..`, `/\.(svg\|png)$/i`) else `activity.icon must be a relative .svg or .png path inside the extension directory`, and must be a file (`activity icon not found: <icon>`); `title` / `title_zh` non-blank ≤ 64 (`activity.<k> must be a non-empty string (≤ 64 chars)`); `description` / `description_zh` ≤ 200 (`activity.<k> must be a string (≤ 200 chars)`); `order` integer 0–1000 (`activity.order must be an integer 0–1000`), default 100. Unknown keys inside are ignored; `ExtensionInfo.activity` carries only the fields present plus `order` |
| `chatbar` | – | `{ icon?, title?, title_zh?, height?, order? }` = one button on the chat input toolbar (see [Chat-bar entries](#chat-bar-entries)). Checked after `activity`, before `extensions`: non-object → `chatbar must be an object`; `icon` same rule as `activity.icon` (`chatbar.icon must be a relative .svg or .png path inside the extension directory`, `chatbar icon not found: <icon>`); `title` / `title_zh` non-blank ≤ 64 (`chatbar.<k> must be a non-empty string (≤ 64 chars)`); `height` integer 80–480 (`chatbar.height must be an integer 80–480`), default 160; `order` integer 0–1000 (`chatbar.order must be an integer 0–1000`), default 100. Unknown keys inside are ignored; `ExtensionInfo.chatbar` carries only the fields present plus `height` and `order` |
| `description` / `homepage` / `license` | – | ≤ 200 chars / http(s) URL / free string, display only |
| `source` | – | https URL of this extension's own `update.json` (`/^https:\/\/\S+$/` + `URL.canParse`, else `source must be an https URL (of the update.json)`); omitted = `<hub_base>/<id>/update.json`. See [Updates](#updates-updatejson) |

No `keepAlive` / `readonly` field: both are derived from `capabilities` (see MRU). No `minHaloVersion`: compatibility is the protocol version carried in `init`. A minimum Halo version for a *release* lives in its `update.json` (`minHalo`), checked before an update is offered or `ext.sh install <id>` downloads it — never at scan time.

### Atomic install (`install.ts`, mirrored by `ext.sh`)

Every writer follows six steps so the root watcher sees one rename per change: unpack into `.tmp-unpack-<rand>` → strip one wrapper directory (`zip -r glb.zip glb/` shape) → pre-check with the scanner's own `readExtensionDir` → move existing `<id>/` aside to `.old-<id>-<rand>` → rename staging → `<id>/` → remove `.old` (on step-5 failure it is moved back; the removal itself retries 3 times and, if it still fails, only logs `[Extensions] could not remove the previous copy …` — the install already succeeded, and the dot-named leftover is skipped by the scanner). The unpack refuses entries with absolute paths, `..`, NUL, or symlink mode bits. Same id = upgrade *or downgrade* — there is no version comparison. `expectId` (skill path, update route) must match the manifest id; `expectVersion` (update route only: the update.json `version`) must match the manifest version; the admin upload takes whatever the manifest says. A failed pre-check never touches a working install. A **fresh** install (no `<id>/` before) drops any on / off entry left in `.state.json` (a manual `rm -rf` leaves one), so it starts on; replacing an existing `<id>/` keeps the switch — see [On / off](#on--off).

## Server

**Registry** (`registry.ts`). `scanExtensions()` runs at boot and when the watcher fires — never per request; routes read the cached `getSnapshot()` = `{ extensions, disabled, errors }`: valid extensions go to `disabled` when switched off (see [On / off](#on--off)); `getExtension(id)` looks in `extensions` only, `getInstalledExtension(id)` in both. Directories starting with `.` (staging, `.old-*`, `.state.json`) are skipped; a non-dot directory whose name isn't a valid id is listed as an error. `installedAt` = directory mtime, which the final rename refreshes (drives newest-wins). `parseManifest` is pure and takes an `entryExists` callback so it is unit-testable without a disk layout.

**Watcher** (`watcher.ts`). Non-recursive `fs.watch` on the root (same shape and same trade-off as `ws/git-dir-watcher.ts`): every install path ends in a rename *into* or an rm *of* a direct child, so one inode suffices and recursive-watch flakiness is avoided. Event burst → 300 ms debounce → rescan → compare `snapshotKey` (`id@version#installedAt` per switched-on extension, the same prefixed `-` per switched-off one, `!id:error` per error row) → broadcast `extension:changed` (the **full** `ExtensionsSnapshot`, global `broadcast()`, not a diff) only if the key changed, so `.tmp-*` churn is silent; after a broadcast it re-judges the cached update verdicts (`rejudgeExtensionUpdates`, no network). `error` → close, retry after 1 s. `rescanAndBroadcast()` is the single notifier: routes call it after their own writes so the response and the next `GET` are already fresh, but never broadcast themselves. Not started in AgentCore mode (no admin editor there).

Why not a "rescan" endpoint for the skill: an agent's shell has no admin cookie, so it would need a second auth scheme, and the admin-upload and skill paths would diverge. With `fs.watch` both converge on the same code with zero auth surface.

**Routes** (`routes/extensions.ts`, mounted under `/api`)

| Route | Auth | Notes |
|---|---|---|
| `GET /extensions` | cookie | `ExtensionsSnapshot` (on + off + errors) |
| `POST /extensions/install` | cookie | multipart `file` = zip, `MAX_ZIP_BYTES` 100 MB (413 by `Content-Length`, then by `file.size`); 400 `{error}` on `ExtensionInstallError`, 500 otherwise |
| `PATCH /extensions/:id` | cookie | `{ enabled: boolean }` = target state (a repeat is a no-op: no write, no push) → `{ ok, id, enabled }`; 400 bad id / body, 404 not installed or an error row (those can only be removed) |
| `POST /extensions/:id/update` | cookie | One-click update, no body — see [Updates](#updates-updatejson); 200 = the new `ExtensionInfo` |
| `DELETE /extensions/:id` | cookie | `rm -rf` + drop its `.state.json` entry; 404 if not installed |
| `GET /extensions/token` | cookie | `{ token, expiresAt }` — asset token, 24 h |
| `GET /extensions/:id/:version/:token/*` | **token in path** | static asset, below |

### Asset serving and the scoped token

The iframe first shipped as `sandbox="allow-scripts"` **without** `allow-same-origin` — an opaque origin. Measured (Playwright): the document navigation itself still carries the admin cookie, but **every subresource** it loads — classic/module `<script>`, `<img>`, CSS, `fetch`, wasm, dynamic `import()`, `Worker` — is a cross-site request with **no cookie**; module scripts, `fetch` and wasm additionally need `Access-Control-Allow-Origin`. The original design assumed subresources would inherit the cookie; they don't. And a `?token=` query does not survive either: the document resolves `./viewer.js` against its own URL and drops the query. That is why the asset credential lives in the path. (The host has since added `allow-same-origin` — see Host, below — for a reason the token can't solve: a cookie-auth proxy in front of halo. The token stays the asset route's one auth path regardless.)

So the credential travels as a **path segment**, which relative URLs inherit for free:

1. Admin calls `GET /api/extensions/token` (cookie-authed) → `mintScopedToken('ext', 24h)` = jwt `{ scope:'ext', iat, exp }` signed with the same secret as the login cookie.
2. Iframe `src` = `/api/extensions/<id>/<version>/<token>/<entry>`; `./decoders/x.wasm` inside resolves to `…/<token>/decoders/x.wasm`.
3. `authMiddleware` lets `EXTENSION_ASSET_PATH = /^\/api\/extensions\/[^/]+\/[^/]+\/[^/]+\/./` through without a cookie (≥ 4 segments, so it never overlaps list / install / token / `:id`); the route itself calls `verifyScopedToken(token, 'ext')` → else 401.
4. **The token can't be replayed as a login.** `validateToken` — the cookie check, shared with the WS upgrade's `isAuthenticated` — returns null for any payload that has a `scope`. The token appears in URLs and access logs, so it is good for exactly one thing: reading extension static files (any installed extension's, nothing else).

`resolveAsset(id, version, rest)` returns null (→ 404) unless: `id` is valid and installed *without error*; `version` **equals** the installed version; no path segment is empty, `.`, `..`, dot-prefixed or contains `\`; the `realpath` stays inside the extension's real directory (symlink guard; both sides realpath'd because the root may itself sit under a symlink); the target is a regular file. Response headers: `Content-Type` from `assetMime` (core's image table + html/js/mjs/css/json/**wasm**/fonts/bin), `Access-Control-Allow-Origin: *`, `Referrer-Policy: no-referrer` (token stays out of `Referer`), `Cache-Control: public, max-age=31536000, immutable`. The version in the URL *is* the cache key — an upgrade changes it. A stale tab holding the old version gets 404, which is the "reload me" signal. No CSP is set here; an extension can ship its own `<meta>` CSP.

### `PUT /files/raw` (save write-back)

`PUT /files` is utf-8 text only and `POST /files/upload` always writes under `.halo/uploads/`, so binary write-back got its own route in `routes/files.ts`: `?path=&projectId=[&expectMtime=][&create=1][&append=1]`, body = raw bytes, file **must already exist** (404 — save never creates) unless `create=1`, directories refused, path validated like the other file routes. If `expectMtime` is given and `Math.round(stat.mtimeMs) !== Math.round(expectMtime)` → `409 { error:'conflict', mtime, size }`; otherwise write and return `{ ok, path, mtime, size }`. The compare is a rounded float compare, so the baseline must be the `modifiedAt` from `GET /files/stat` (float ms). `create=1` creates a missing file (parents `mkdir -p`); `append=1` uses `appendFile` and ignores `expectMtime` — both exist for bundle `fs` write / append. `root=<dir>` (the bundle host always sends its bundle path) requires `<dir>` to be an existing directory with `path` strictly inside it, else `404 { error:'Bundle root not found' }` and nothing is created — so a bundle deleted / renamed mid-recording is never resurrected at its old path by `create=1`'s `mkdir -p`.

## Admin host

### Subscribable registry and resolution (`previews/registry.ts`)

Two layers behind one lookup: `builtins` (the eight compile-time plugins) and `snapshot` (runtime extensions). Every mutation `bump()`s a version counter; `useRegistryVersion()` is a `useSyncExternalStore` over it, so `FilePreview` and the editor's MRU effect re-resolve on change. The snapshot is fed by `GET /extensions` at workspace open, each `extension:changed` frame, and a re-fetch on WS reconnect (`state-handlers.ts`) — **no polling**. `editor-panel.tsx`'s old module-level `BINARY_EXTENSIONS` snapshot is gone; `isBinaryExtension(ext)` reads the registry live.

**Initial load (`loadExtensions()`).** The page's one `GET /extensions` is a single shared promise: `workspace-layout.tsx` kicks it off in parallel with the workspace resolve, and the editor's one-shot routing awaits the same request. Until it lands, "list not loaded" looks exactly like "nothing installed", and a wrong text verdict opens — and on tab restore persists — the file as text (a reloaded `.glb` tab came back as text this way). So `isBinaryExtension(ext)` (click-open, tab restore after reload, open-to-side) is async: a *preview* verdict (`NON_TEXT_FALLBACKS` or `canPreview(ext)` already true) returns at once, since extensions only add viewers ahead of text and `FilePreview` re-picks the viewer when the list lands; a *text* verdict awaits `loadExtensions()` first, because an extension may claim an extension-only type (`.glb`) or a text suffix (`.json`). The wait is capped at `INITIAL_LOAD_WAIT_MS` (3 s), counted from the first call, so a request hung on a dead connection (sleep / wake) can't block every open; past the cap it routes as if nothing were installed (`.glb` opens as text). The request isn't cancelled — a late list still lands through `setExtensions` and bumps the version. It never rejects and is never re-issued: a failed fetch leaves the layer empty without delaying later opens, and the WS-reconnect re-fetch / `extension:changed` fill it in.

`resolve(ext)` returns every way to open the file, best first:

1. `default` extensions, **newest `installedAt` first**
2. the built-in plugin, if any
3. `option` extensions (same ordering)
4. `text` (Open as Text) — always present, always last

Errored extensions never appear. With nothing installed this is `[builtin, text]` / `[text]` — identical to pre-extension behavior, and the open-with menu (rendered only when `candidates.length > 2`) stays hidden, so **zero installs = zero visible change**. Deliberate difference from VS Code: with several `default` handlers VS Code asks and remembers the answer in `editorAssociations`; we have nowhere to remember it, so newest-install wins deterministically and the user switches via the menu. Ext-less files (`''` can't be in a manifest) always go to the text editor.

**Open with** (`ui/open-with-menu.tsx`, state in `FilePreview.Dispatch`): picking a candidate sets a per-tab `override` — never persisted, forgotten when the tab closes; it is looked up by `resolvedKey` in the live candidates so an upgraded extension renders its fresh `info`. Picking `text` calls the existing `onOpenAsText`. Switching away from a dirty extension asks `confirmAction("… Discard them and switch viewer?")`.

### Iframe host (`extension-host.tsx` + `extension-host-logic.ts`)

The split is deliberate: `extension-host-logic.ts` is a **pure state machine** (`onClientFrame`, `onLoaded`, `onPutResult`, `onConflictChoice`, `onFileChanged`, `onSaveRequest`, `onThemeChange`), each taking `HostState` + one input and returning `{ state, effects[] }`; the React component only executes effects (`post`, `load`, `put`, `set-modified`, `error`, `confirm-conflict`, `warn`). That is what makes the protocol unit-testable frame by frame.

- Mount: `getExtensionToken()` → iframe `src` (`extension-token.ts`: module-level cache, in-flight dedupe, re-mint when < 60 s to expiry; an already-mounted iframe is never refreshed — it has its assets already).
- Attributes: `sandbox="allow-scripts allow-same-origin" allow="" referrerpolicy="no-referrer"` — the same grant as `html-preview.tsx`. `allow-same-origin` was withheld in the first cut (the path token made the cookie unnecessary for *halo*), but a cookie-auth reverse proxy in front of halo — the dev/prod CloudFront + midway Lambda, and equally oauth2-proxy / Cloudflare Access — authenticates **every** request by its own cookie, and an opaque-origin iframe sends none on module scripts / `fetch` / wasm (measured: classic `<script>` / `<img>` / CSS still carried the proxy's `SameSite=None` cookie; `mode: cors` requests carried nothing). The proxy 307'd `model-viewer.min.js` to its login page → the browser reported a CORS error → no `ready` → "extension unresponsive" after 10 s. Nothing halo-side can add a cookie to those requests; only `allow-same-origin` makes them first-party again. Trade-off accepted: the extension now runs in the admin's origin and can reach `parent.document` and the cookie-authed API — same boundary as an HTML preview, trust model "code the user chose to install" (like a skill).
- Sender check is `e.source === iframe.contentWindow` plus the `haloExt: 1` marker on every frame. `e.origin` is the admin's own origin for every extension iframe and can't distinguish two extensions.
- The extension never fetches the file: the host fetches `viewUrl` (streaming, no 10 MB cap) as an `ArrayBuffer` plus `GET /files/stat` for the mtime baseline, and **transfers** the buffer in `load`. `targetOrigin` is `'*'` (kept from the opaque-origin days; the frame only carries the file bytes the extension is about to be shown anyway).
- No `ready` within 10 s → "extension unresponsive" with Retry / Open as Text. `error` frame → banner above the iframe. Files > 100 MB (`EXTENSION_MAX_BYTES`, client memory) show the too-large placeholder instead of mounting.

```
 |-- load{buffer,mtime} ----------->|  render
 |<--------- dirty{true} -----------|  markModified(path) → tab dot
 |   user clicks Save               |
 |-- save-request ----------------->|
 |<--------- save{buffer} ----------|
 |   PUT /files/raw?expectMtime=…   |
 |-- saved{mtime} ----------------->|  200        (409 → conflict flow below)
```

### Theme tokens

- `themeVars` (in `init` and every `theme` frame) is the admin's current semantic palette, forwarded verbatim: the 16 tokens `background`, `foreground`, `card`, `card-foreground`, `border`, `input`, `primary`, `primary-foreground`, `secondary`, `secondary-foreground`, `muted`, `muted-foreground`, `accent`, `accent-foreground`, `destructive`, `ring` (`EXTENSION_THEME_TOKENS`, shadcn naming = globals.css `--<token>` without the `--`). Values are CSS color strings as the admin theme declares them (hex today; `rgb()` / `oklch()` pass through untouched); a token the theme leaves empty is omitted.
- Recommended use: set each as `--halo-<token>` on the extension's own `:root` and reference those, with the extension's own values as the fallback — older hosts send no `themeVars`, so treat it as optional.
- `theme` is `light` \| `dark` derived from the rendered `--background` (WCAG relative luminance > 0.4 → `light`; the host paints it onto a 1×1 canvas so any CSS color notation resolves to sRGB). Use it for `color-scheme` or anything not covered by the palette. There is no theme-name table: `warm` (#f6f1e7, luminance 0.88) is now correctly sent as `light` — the old `theme === 'light' ? 'light' : 'dark'` sent it as `dark`.
- The host reads the palette off `<html>`'s computed style whenever `useTheme().theme` changes; the theme provider stamps `data-theme` in the same tick as its `setState`, so the DOM is already the new theme by then. A new admin theme only has to define the same 16 variables in globals.css — neither the host nor any extension changes.

### Dirty, save, conflict

- `dirty` mirrors into the editor store (`markModified` / `clearModified`), so the tab dot and the existing close-tab `confirmAction` work unchanged. Unmounting or reloading with a dirty doc clears the dot with it.
- Save trigger is the toolbar **Save** button → `requestSave` → `save-request`; `editor-panel.handleSave` also forwards to the mounted host via `getExtensionHost(projectId, path)` (a module-level registry keyed by panel + path, same shape as `face-bridge.ts`). 5 s without a `save` reply → alert "did not respond".
- `file:changed` for an extension tab is routed by `editor-panel` to `host.fileChanged()` → stat → `onFileChanged`: ignored when `diskMtime <= state.mtime` (our own save's echo) or when dirty; otherwise re-`load`.
- **409**: `onPutResult` emits `confirm-conflict`. `confirmAction` is yes/no, so the three-way choice is two chained questions — *Overwrite the disk version?* yes → re-PUT once with the 409's mtime as `expectMtime` (`retried`; a second 409 → `save-error{conflict}` + banner); no → *Discard your changes and reload?* yes → re-`load`, no → cancel (stay dirty). IO failure → `save-error{io}` + banner, stays dirty.

### Export

An extension that can render its document as an image (draw.io *File ▸ Export as*, Excalidraw *Export PNG / SVG*) can't hand the user a download: the iframe sandbox has no `allow-downloads` (adding it didn't help — draw.io raised neither a save picker nor a download event). Instead the extension sends the bytes to the host, which writes them **into the workspace, next to the open file**.

- **Who may export**: a `save`-capable, non-bundle extension — the host sends `init.export: true` exactly then. No separate manifest capability: a 1.5.9 registry rejects unknown capability values, so a new one would make the extension uninstallable on older hosts; riding on `save` keeps one zip working everywhere (older hosts omit `init.export`, the extension hides its export UI).
- **Validation** (`extension-host-logic.ts` `onExportFrame`): before `ready` → ignored + warn; no `save` / bundle → `export-error{denied}`; `name` not a plain file name (empty, `.` / `..`, contains `/` `\` NUL) or equal to the open file's own name → `export-error{invalid}`; `buffer` not an ArrayBuffer → `invalid`. All of these do no I/O.
- **Write** (`extension-host.tsx`): target = open file's directory + `name`; `stat` it, and if it exists `confirmAction` "already exists — overwrite?" (declined → `export-error{cancelled}`); then `PUT /files/raw?create=1`. Success → `exported{name, path}` + a banner "Exported to <path>" with a Download link (`/files/download`); failure → `export-error{io}` + banner. Exporting never touches the dirty state or the open file. Replies for a since-remounted iframe are dropped (same guard as `fs`).
- Extensions name the file `<stem>.<ext>` from `init.file.name` (draw.io's own `filename` is odd — `-Order flow.drawio.png` — so only its extension is kept). drawio 1.1.0 turns on draw.io's `exportProtocol: 1` only when `init.export` is true.

### MRU, keep-alive, upgrade, uninstall

- `editor-panel` keeps the last 5 preview tabs mounted (`PREVIEW_CACHE_SIZE`); "heavy" previews mount active-only. `isHeavyPreview` is true for an extension **without** `save` and not `bundle`: nothing to lose on unmount, and each viewer may hold a WebGL context (Chrome caps ~16 per page). An extension **with** `save` stays in the MRU because its dirty state lives only in the iframe; a dirty preview is never evicted past the cap. The mounted previews render in **path-sorted** order, not MRU order: promoting a tab reorders the MRU, React would then move the keyed nodes with `insertBefore`, and moving an iframe in the DOM reloads it — a running emulator or editor would start over on every tab switch. With a stable order, insertions and removals never move the siblings. The active heavy preview's wrapper is keyed by path: `FilePreview`'s `Dispatch` is keyed only by file extension and a host posts the file bytes once per mount, so switching between two heavy tabs of the same type (two `.ipynb`) used to keep showing the first file.
- **Upgrade while mounted** (`extension:changed` gives the tab a new `info.version` — from an upload, `ext.sh`, or the one-click Update): not dirty → remount with the new URL; dirty → non-blocking banner "updated to vX" with a Reload link (`reload` asks to discard first).
- **Uninstall or switch-off while mounted**: not dirty → `resolve()` drops the candidate and the tab falls to the next one (built-in plugin if the ext has one, else the fallback page). Dirty → `Dispatch` keeps rendering the last-shown extension so the edits can still be saved, with a banner picked by whether the id is now in `snapshot.disabled` (`gone: 'disabled'` → "has been turned off", else `'uninstalled'`); the loaded iframe already holds its assets — after an uninstall a fresh load would 404, a switched-off one still serves (assets go through `getInstalledExtension`). Once saved, the tab falls through the same way.
- **Fallback page** (`UnsupportedPreview`): "This file type has no built-in preview. Extensions for more file types are available at halo-hub ↗" + Open as Text / Download. A switched-off extension that claims the suffix adds one line, `"<name>" is turned off — turn it on in Settings → Extensions.` (`disabledFor()`, the only reader of `snapshot.disabled` outside Settings). The link is a constant — no lookup, no per-ext URL, no online recommendation (would need a network call or a bundled index that goes stale).
- **Settings → Extensions** (`features/settings/extensions-view.tsx`): upload zip, **Check for updates** + "Last checked hh:mm" in the header, and one id-sorted list of on and off extensions (off rows dimmed with an "Off" tag; errors in red). Each valid row has, in order, an **Update** button when its verdict is `available`, a `role="switch"` on / off toggle (PATCH) and Remove (`confirmAction`); error rows get Remove only. Update, switch, upload and remove share one busy flag. The verdict line under a row: `Latest X` (blue, `available`), `X needs Halo Y — upgrade Halo first`, `No update info at the source`, `No update source configured`, or the error for `invalid` / `refused` / `unreachable`; a verdict shows only when its `id@installed` matches the row's `id@version`, so a stale one never sits on a just-updated row. It never re-fetches after a mutation — `extension:changed` and `updates:changed` update it.

### Immersive maximize

Maximizing the canvas on a **viewer** extension (an emulator, a model viewer) hides every bit of chrome around it. The predicate is `isImmersiveViewer(info)` in `registry.ts`: any extension **without** `save`, bundles included (a bundle's state lives in its own directory, not behind a Save button). It is *derived* — `editorStore.maximized` stays the only persisted state, and leaving immersive is `setMaximized(false)`; the extension host decides (it knows which candidate actually rendered), publishing itself through `claimImmersive()` (`features/editor/immersive.ts`) while `maximized` is on and the pane's active tab (`ImmersivePane` context, provided by `EditorPanel` for the focused pane only) is its path.

- **Pure CSS.** While immersive, the host's banners + iframe region become a `fixed inset-0 z-[70]` overlay, and `EditorPanel` / `workspace-layout` class-hide the panel header, tab bar, non-focused panes and the floating bottom panel (`hidden`, never unmounted). The iframe is never reparented or remounted, so the viewer keeps its state.
- **Real fullscreen** only from the maximize click: the button calls `armImmersiveFullscreen()` (valid for that click's task), and the host that goes immersive takes the arm inside the click's user activation and requests fullscreen on `<html>`. A `maximized` restored from localStorage has no activation and stays in-page. The browser or Electron ending fullscreen ends immersive too (one Esc, one exit) — unless the viewer had its own fullscreen (an emulator's canvas), which keeps that Esc.
- **Exit**: **Esc** — the iframe is same-origin, so its keydown is watched inside each loaded document (the viewer's own fullscreen takes that Esc first) — or the top pill (`editor.immersive.exit`, "× Exit · Esc"). Mouse: top-centre, shown for 2.5 s on entering, pinned while the pointer is within 48 px of the viewport top (watched by listeners, no hot zone over the iframe), hidden 1.5 s after it leaves. Touch: always on screen as a compact × at top-left, where viewers keep their title label; a tap in the top band widens it for 3 s, and the pill exits only for a press that started on it. On exit the host hands focus back to the iframe, except for "Back to chat".
- **Reply toast.** The chat is hidden, so when any loaded chat tab's turn settles while immersive (`workspace-layout`, the same hook as the finish notification) an in-page toast (`z-[80]`, ~8 s, newest session first) says "Agent replied · <title>" (or "N sessions replied") with **Back to chat**: it exits immersive without refocusing the iframe, opens that session's tab, switches the bottom panel to Chat and dispatches `halo:focus-chat-input` so the caret lands in the composer (`message-input.tsx` listens). The toast is dropped as soon as immersive ends.
- The host file picker (`pick`, below) renders in a body portal at `z-[90]`, above the overlay and its toast.

### Bundle extensions

A `bundle: true` extension opens a **directory** whose name ends in one of its suffixes (`Standup.htrans/`) — a package the extension owns, first user `htrans` (meeting recorder). Routing is separate from files: `resolveBundle(ext)` lists bundle extensions only, `resolve(ext)` never does (a *file* `x.htrans` is untouched), and `isBundleName(name)` = a `default` bundle extension that runs here claims the suffix.

- **Explorer**: such a directory gets a package icon; clicking (or Enter on) the row opens it as a preview tab like a file, double-click too; only the chevron expands it, so its contents stay browsable. Context menu adds Open to the Side. "New File" with a bundle suffix runs `mkdir` and opens the new bundle — both the tree's inline New File and the Explorer header's New File button (which would otherwise create an empty file no extension can open). The tab has no Open as Text / Download. Persisted tabs carry `bundle: true`; on restore the tab reopens only if a bundle extension still claims it, otherwise it is dropped (the directory is never read as text).
- **Access**: no `load`; the extension reads and writes inside its directory with `fs` frames. The host maps them to `GET /files/download?inline=1` (read), `GET /files/tree` (list), `GET /files/stat` (stat) and `PUT /files/raw?create=1&root=<bundle>[&append=1]` (write / append; a vanished bundle → `not-found`), and serializes write / append **per path** (`createKeyedQueue`), so appends land in request order; other ops run concurrently. `file:changed` never reloads a bundle.
- **Busy**: `dirty: true` = "recording, don't drop me" → tab dot, close confirm (also when the same bundle is open in the other split pane — each pane runs its own iframe), MRU pin, page-unload warning: the browser always shows its generic beforeunload prompt; the desktop shell shows a native confirm, which the admin only triggers while a tab is busy or unsaved. Deleting, renaming or drag-moving a busy bundle (or an ancestor directory) asks the same close confirm first, then closes the tab **before** the file operation. Ctrl+S / Save does nothing on a bundle tab. Bundle extensions are never heavy (they stay in the MRU like `save` extensions). fs results that arrive after the iframe was remounted (retry / upgrade) are dropped.

### Scoped file access and the picker (`fs-read`)

A viewer extension (emulator, model viewer) otherwise sees only its own file or bundle. `fs-read` lets it read elsewhere on the machine and lets the user choose what to read. UX gating in the host, **not** an isolation boundary: the iframe is same-origin with the admin cookie and could call `/api/fs/raw` itself, which is why the guard below sits on the routes.

- **`fs` with `scope`** (`extension-host-logic.ts` `onFsFrame`): `workspace` → the same `/files/*` read routes with a workspace-relative path; `system` → admin-cookie routes by absolute path: `read` → `GET /fs/raw` (streamed bytes), `stat` → `GET /fs/stat`, `list` → `GET /fs/browse?files=1` (name + type per entry). Validation happens before any request: `isSystemPath` (POSIX `/…` or `C:/…`, forward slashes, no NUL, no empty / `.` / `..` segment); unknown scope or op, a missing capability, or `write` / `append` → `fs-result{denied}`; a bad path → `invalid-path`.
- **`pick`**: opens `FilePicker` (`shared/components/file-picker.tsx`) — a whole-machine browser with Workspace and Home shortcuts, a path box, a breadcrumb and the `accept` filter (directories always show; keyboard: arrows / Enter / Backspace for up / Esc cancels, the capture listener swallowing Esc before maximize sees it). One picker at a time, tied to the iframe attempt that asked; a reply for a since-remounted iframe is dropped. If the viewer is in its own fullscreen the host first drops back one level, so the picker isn't covered. On pick, the host `stat`s both the file and the workspace and compares **realpaths**, so a symlinked workspace or ROM dir lands on the right side: inside → workspace-relative `path`, else the absolute one. Closing it answers `cancelled`.
- **Hidden-path guard** (`routes/files.ts`): `/fs/stat`, `/fs/raw` and `/fs/browse?files=1` all refuse the sandbox hidden lists (`~/.halo/secrets`, `~/.ssh`, `.git-credentials`, the global dbs …) via `isHiddenHostPath` (exported from `tools/sandbox.ts`; no second list), judged on the **realpath** so a symlink can't reach them. A refused path answers with the same 404 and message as a missing file, and a listing silently omits hidden entries. `/fs/browse?files=1` lists the same noise-filtered tree as `/files/tree` but with dot-entries shown and symlinks counted as what they point at; `sizes=1` adds file sizes. The default folder-picker response is unchanged. See [dev/api.md → Filesystem browse](../dev/api.md#filesystem-browse-not-project-scoped--for-the-workspace-picker).
- Settings → Extensions shows a "Reads files on this machine" tag for an extension that declares it.

### Platforms

`currentPlatform()` (`registry.ts`, computed once): UA contains `Electron/` → `desktop-mac|win|linux` by OS, else `web`. An extension whose `platforms` excludes it is skipped by every resolve (routes as if not installed; a bundle directory is a plain folder), the fallback page says `"<name>" only runs on: …`, and Settings → Extensions shows a platforms badge plus a gray "not supported here" tag.

### Activity-bar entries

Manifest `activity` gives an extension one button in the admin's leftmost activity bar; clicking it shows `entry` as a full-width page in the main area — no sidebar, like Agents / Settings. A page and a file viewer can live in one extension (`extensions` non-empty), or the extension opens no files (`extensions: []`).

- **Placement.** `activityEntries()` (`previews/registry.ts`) = valid extensions with `activity` that `runsHere`, sorted by `activity.order` (default 100) then id. `workspace-layout.tsx` renders them after the built-in top tabs (after Cron) and before the bottom group (Settings, quick toggles); built-in order never moves. It reads the list under `useRegistryVersion()`, so an install / uninstall arrives with the `extension:changed` push — no polling. Nothing installed = no button = no visible change.
- **Label.** Title: zh `title_zh` → `title` → `name`; en `title` → `name`. Hover-drawer description: zh `description_zh` → `description` → top-level `description` → `''`; en skips the `_zh` variants. The title is also the button's `aria-label`; the drawer reuses `ActivityBarLabel`.
- **Icon.** `activity.icon` renders as a 20×20 span with `background-color: currentColor` and `mask` / `-webkit-mask: url(/api/extensions/<id>/<version>/<token>/<icon>) center / contain no-repeat` (`ExtensionActivityIcon`), so it follows the active / hover colour and every theme, and the SVG never enters the DOM (the asset route serves `.svg` as `image/svg+xml`, which masks require). An empty box of the same size while the asset token is being fetched (so the generic icon never flashes first); lucide `Puzzle` when there is no `icon` or the token request fails.
- **Click / lifetime.** Through the same `handleTabClick` as built-ins (exits editor maximize). Tab id `ext:<id>`. The page (`ExtensionActivityPanel`, `features/workspace/extension-activity-panel.tsx`) mounts only while its tab is active: switching away unmounts the iframe, so its timers, polling and audio stop; nothing is kept across visits. Keyed by `id@version`, so an upgrade remounts. Same iframe grant as the file host (`sandbox="allow-scripts allow-same-origin"`, `allow` = `MEDIA_ALLOW` with `media` else `''`, `referrerpolicy="no-referrer"`).
- **Persistence.** `halo_sidebar_tab` may hold `ext:<id>`. After a reload the layout waits for `loadExtensions()` (3 s cap); if the id is then not in `activityEntries()` — uninstalled, broken, or excluded on this platform — it falls back to Explorer. The same rule fires when the extension disappears while its page is open. Never while the list is still loading (same three-state idea as the hidden Source Control tab).
- **Protocol.** `extension-activity-logic.ts` (pure, effects like the file host's): `ready` → `init` with `view: 'activity'` — `protocol`, `capabilities`, `theme`, `themeVars`, `platform`, `lang`; no `file` / `bundle` / `export` / `jupyter` — re-sent on every later `ready`; `error` → banner above the iframe; `theme` / `lang` frames on change, after `ready` only. `dirty` / `save` / `fs` / `pick` / `export` are ignored with a `console.warn('[ExtensionActivity] …')`. Granted `capabilities` = `media` / `transcribe` / `stt-local` from the manifest (the ones that work without a file); `save` / `fs-read` are not granted. No `ready` in 10 s → the `editor.extension.unresponsive` message with Retry (remounts the iframe).
- **Settings → Extensions** shows an "Activity bar" tag for such an extension, and drops the suffix line when `extensions` is empty.
- **Short viewports.** The top group (built-ins + extension buttons) is a scroll container (`min-h-0 flex-1 overflow-y-auto`, scrollbar hidden) in place of the old `flex-1` spacer, so Settings and the quick toggles never get pushed off-screen. The quick-toggles popover sits in the bottom group, outside the scroller, so it isn't clipped.
- **Data for the page.** A page served from the admin origin carries the admin cookie, so it can call cookie-authed routes; `/api/show/*` (the Halo City data) accepts that cookie as `full` — see [dev/api.md → Show](../dev/api.md#show-world-snapshot).

### Chat-bar entries

Manifest `chatbar` gives an extension one button on the chat input toolbar; clicking it opens `entry` in a small panel above the input box, and the extension may put text into the draft — the first user is the hub's voice-input extension (record → server-side local transcription → text at the caret). Like `activity`, it can sit beside a file viewer or stand alone (`extensions: []`); one extension may declare both.

- **Placement.** `chatbarEntries()` (`previews/registry.ts`) = valid extensions with `chatbar` that `runsHere`, sorted by `chatbar.order` (default 100) then id. `ExtensionChatbarControl` (`features/chat/extension-chatbar-control.tsx`) renders one 32×32 button each, right after the capture control in `message-input.tsx`, reading the list under `useRegistryVersion()` — installs / uninstalls arrive with `extension:changed`, no polling. Nothing installed = no button.
- **Label / icon.** Tooltip and `aria-label`: zh `title_zh` → `title` → `name`; en `title` → `name` (`chatbarTitle`). `chatbar.icon` is the same `currentColor` mask as the activity icon (shared `ExtensionMaskIcon`, `previews/extension-icon.tsx`), 16×16; blank while the token loads, lucide `Mic` when there is no `icon` or the token request fails.
- **Panel.** Portaled to `<body>` as `fixed z-[55]` over the input's wrapper — the chat dock's Panel clips its overflow, so an in-tree panel lost its title bar under the editor. `chatbarPanelBox` (`extension-chatbar-logic.ts`): width `min(420, viewport − 16)`, left = wrapper + 12 clamped 8 px inside the viewport, bottom 4 px above the wrapper; a thin title bar (title + ×, 28 px) over an iframe area of `chatbar.height` px, squeezed to what fits above the wrapper (floor 80 px — then the panel overlaps the input's top, title bar still 8 px inside the viewport). While open it re-measures on a ResizeObserver over the wrapper and every ancestor (a dock-divider drag moves without resizing it), window resize / scroll (capture) / pointermove (the floating chat drags by position), rAF-batched — only `style` changes, the iframe never remounts. A wrapper measuring 0×0 (chat tab on the terminal, dock collapsed — `hidden`, not unmounted) or a chat-tab switch (`activeTabId`; one MessageInput serves every tab) closes it. One panel at a time: another button switches, the same button / × / Esc on the host page closes it (Esc in the textarea closes it before the "Esc interrupts the turn" rule). A click outside does **not** close it — the user may edit the draft while dictating.
- **Lifetime.** The iframe exists only while the panel is open (`ExtensionPageFrame`, keyed `id@version`); closing unmounts it, so the microphone stops. A user close (its button / × / Esc) of a panel that last reported `busy: true` is graceful instead: `close-request` is posted and the panel stays — button still active, `insert-text` still landing — until `busy: false`, 35 s (`CHATBAR_CLOSE_TIMEOUT_MS`, above the extension's own 30 s), or a second user close. State: `chatbarReducer` (`{ openId, busy, closing }`) held by `MessageInput`. A chat-tab switch, a hidden input, uninstalling (or a platform exclusion) of the open extension, or opening another panel unmounts at once, busy or not. Same grant as the activity page: `sandbox="allow-scripts allow-same-origin"`, `allow` = `MEDIA_ALLOW` only with `media`, `referrerpolicy="no-referrer"`. No `ready` in 10 s → unresponsive + Retry inside the panel.
- **Protocol.** `extension-chatbar-logic.ts` (`onChatbarFrame`, pure; shares state / init / theme / lang with the activity logic): `ready` → `init` with `view: 'chatbar'` (same fields as `'activity'`), re-sent on every `ready`; `error` → banner; `theme` / `lang` after `ready`; `insert-text` → insert (rules in the protocol table); `busy` → the panel's close behaviour (see Lifetime); `dirty` / `save` / `fs` / `pick` / `export` ignored with `console.warn('[ExtensionChatbar] …')`. Granted `capabilities` = manifest ∩ `media` / `transcribe` / `stt-local`. There is deliberately **no send frame** (v1 product decision: an extension can fill the draft, only the user sends).
- **Insert.** `MessageInput` replaces the textarea's current `selectionStart`–`selectionEnd` with the text (`insertAtSelection`), through its own `setText` (so the draft, `@` detection and auto-grow behave as for typing), and puts the caret right after it. It does **not** focus the textarea — focus stays in the iframe, whose keyboard controls keep working. Works while a turn is running (it only edits the draft).
- **Settings → Extensions** shows a "Chat bar" tag for such an extension.

### Extension settings

An installed extension with manifest `settings` gets one Settings section (`settings-schema.ts` `extensionSections()`, built from the registry's cached snapshot): `source: 'extension'`, namespace `ext-<id>` (prefixed so an extension id can't collide with a skill / provider namespace), title = manifest `name`, every field `globalOnly`, secrets `secret: true` (masked). Values live in the global `~/.halo/secrets/settings.yaml` at `ext-<id>.params.<key>` / `ext-<id>.secrets.<key>` and go through the ordinary `/settings` routes (workspace scope refused by the global-only backstop). Admin: Settings nav group **Extension settings** under Extensions. A switched-off extension gets no section, like an uninstalled one, but its values stay in `settings.yaml`: `extensionOffNamespaces()` (its `ext-<id>` plus the ids of the skills it ships) keeps them out of the Orphans list, so they can't be pruned there and come back on re-enable. Values never reach the manifest, the hub or the `init` frame — only server code reads them (`getServerParam` / `getServerSecret` in `config.ts`, read per use, so no restart).

### Streaming transcription proxy

WS `/api/transcribe/stream?ext=<id>&lang=<auto|xx-XX|xx-XX,yy-YY,…>` (`routes/transcribe-ws.ts`) relays an extension's live audio to **Amazon Transcribe streaming** so AWS credentials never reach the browser. Every WS endpoint (`/ws` admin socket, this proxy, `/api/jupyter/channels`) is a `noServer` ws server behind one http `upgrade` listener, `ws/upgrade-router.ts` (`createUpgradeRouter`: exact-pathname lookup in a Map, plain `split('?')` instead of `new URL()` since it runs before auth on raw input; unknown path → `400`; AgentCore mode registers no routes, so every upgrade gets that 400) — a `ws` server attached with `{ server, path }` would 400 every other path's handshake. Upstream client: `@aws-sdk/client-transcribe-streaming`.

- **Handshake**: login cookie (`isAuthenticated`, same as `/ws`) else 401; `ext` must be installed, switched on (`getExtension`) and declare `transcribe` else 403. The extension iframe is same-origin, so its WS carries the cookie.
- **Upstream**: `StartStreamTranscription` (`pcm`, 16 kHz, `ShowSpeakerLabel: true` always — speaker diarization, no switch; the service accepts it together with `IdentifyMultipleLanguages` as well as `LanguageCode`, checked against the live service). `lang=auto` (default) → `IdentifyMultipleLanguages` + `LanguageOptions` = `ext-<id>.params.auto_languages` → manifest default → `zh-CN,zh-HK,en-US` (Cantonese must be a candidate, otherwise it is transcribed as wrong Mandarin text); one code (`^[a-z]{2}-[A-Z]{2}$`) → `LanguageCode`; a comma-separated list of 2–5 distinct codes → `IdentifyMultipleLanguages` + `LanguageOptions` = exactly that list (htrans sends `zh-CN,en-US` / `zh-HK,en-US` for its Mandarin + English / Cantonese + English options); anything else → `error bad-request`, upstream never called. "One dialect per language" in a list is left to Transcribe (its BadRequest maps to `bad-request`). Region `ext-<id>.params.region` → manifest default → `us-east-1`. Credentials: all three of `ext-<id>.secrets.access_key_id` / `secret_access_key` / `session_token` empty → the SDK default chain (`defaultProvider()`); both keys set → static keys (+ `session_token` if set); any other partial set → `error credentials` naming the missing key(s), upstream never called (no silent switch to the machine's identity). All read per connection.
- **Frames**: client binary = PCM s16le mono 16 kHz, text `{"type":"end"}` = flush then server closes 1000. Server text: `ready` (sent on connect — the proxy is taking audio; it can't mean "Transcribe accepted" because the SDK's `send()` only resolves after the first audio event, so a client waiting for that would hit Transcribe's 15 s no-audio timeout; upstream rejections follow as `error`), `partial` / `final` `{start,end,text,lang}` (seconds from this stream's first audio byte), `error {code,message}` then close 1011. **Speakers**: Transcribe puts its `Speaker` label (`"0"`, `"1"`… numbered per stream — a reconnect starts over, and it is never a name) only on the pronunciation items of a *final* result, so a `final` adds `speaker` and a `partial` never has one. `splitBySpeaker()` turns one final result into one `final` frame per speaker run: runs follow the items in order, a pronunciation item with a different `Speaker` opens a new run, punctuation and unlabelled items stay in the current one; each run's text is cut from the result's `Transcript` (not joined from item contents, which would drop the spaces of mixed Chinese / English) at its first item's offset, found left to right with `indexOf`, then trimmed (empty runs dropped), and its `start` / `end` are its first / last item's times. One speaker → the result unchanged plus `speaker`; no labelled item → unchanged without `speaker`; an item that can't be located in the text → the whole result as one frame under the speaker with the most words. A client that ignores `speaker` keeps working — a multi-speaker result just arrives as several `final`s (htrans ≥ 1.0.5 shows `"0"` as "Speaker 1"; the proxy has labelled speakers since 2.0.4). Codes: `credentials` (CredentialsProviderError / UnrecognizedClient / InvalidSignature / ExpiredToken / InvalidClientTokenId), `denied` (AccessDenied), `limit` (LimitExceeded), `bad-request` (BadRequest / bad `lang`), `io` (everything else, incl. > 30 s of audio queued unsent).
- **Lifetime**: the client WS closing aborts the upstream request and destroys the client (no orphan streams). Frames are capped at 1 MiB (`maxPayload`); a protocol violation (oversized frame → close 1009, invalid UTF-8 text → 1007) closes only that socket — each connection has an `error` listener, and the upgrade router never throws on a malformed request-target (unknown path → `400 Bad Request`). Reconnect across Transcribe's 4 h cap / ~15 s silence drop is the extension's job. Logs: `[Transcribe] stream open ext=… lang=… region=…` / `stream closed after Ns` / `stream error … code=…` (error name only) — never audio or credentials.

### Notebook kernels (Jupyter proxy)

The ipynb extension (2.0.0+) runs cells on **real kernels on the Halo machine**. Halo starts a local `jupyter server` on demand and exposes a fixed whitelist of it under `/api/jupyter/*` (`jupyter/manager.ts` process + kernel registry, `routes/jupyter.ts` HTTP + WS). Jupyter is never bundled: the user installs it (`pip install jupyter_server ipykernel`) and every kernelspec it finds is offered.

- **Trust level = the built-in terminal**: kernels run as the Halo service user, unsandboxed; admin cookie only (the HTTP routes sit behind `authMiddleware`, the WS handshake checks the cookie like `/ws`; web-channel / IM / A2A tokens can't reach it); not mounted in AgentCore mode; the child env is `cleanChildEnv()`. No manifest capability gates it — `init.jupyter` is the host's signal (a new capability value would make ipynb 2.0.0 uninstallable on a 1.6.0 registry, same reasoning as `init.export`). The iframe is same-origin with the login cookie, so the extension fetches / opens the WS to `/api/jupyter/*` itself.
- **Settings** (`general.jupyter.*`, globalOnly, read at each spawn — no restart): `enabled` (default `true`) and `path` (default empty = `jupyter` on PATH, else the full path of the executable).
- **Status** (`GET /api/jupyter/status`) never starts anything: disabled → `{enabled:false, available:false}`; executable missing → `available:false` + `error` + `hint: 'pip install jupyter_server ipykernel'`; else `<jupyter> server --version` is run once per resolved path and cached (a failing probe isn't cached, so a later `pip install` is picked up).
- **Server**: one per Halo process, started by the first `kernelspecs` / kernel start (concurrent callers share one start), restarted lazily after it exits. Args: `server --no-browser --ServerApp.ip=127.0.0.1 --ServerApp.port=<free port> --ServerApp.port_retries=0 --ServerApp.root_dir=<filesystem root> --ServerApp.terminals_enabled=False --ServerApp.shutdown_no_activity_timeout=600 --MappingKernelManager.cull_idle_timeout=3600 --MappingKernelManager.cull_interval=300 --MappingKernelManager.cull_connected=True` (+ `allow_root` when Halo itself runs as root). Both spawns (the `--version` probe and the server) pass `cwd: os.homedir()` — inheriting the server's cwd left a live jupyter holding the desktop install dir open, blocking the installer; `root_dir` is unaffected. The random upstream token goes in `JUPYTER_TOKEN` (env, not argv — `ps` would show it) and every upstream call sends `Authorization: token …`. Ready = `GET /api/status` answers, within 30 s, else 503 with the stderr tail. When the process exits, the kernel Map is cleared and every client socket closes 1011.
- **Kernel start** (`POST /api/jupyter/kernels {projectId, path, name}`): `resolveProjectPath` + `validatePath` (symlinks followed; outside → 400), then the **real path of the notebook's directory** is sent as the upstream kernel `path`. jupyter_server 2.x `cwd_for_path` splits that on `/`, joins the parts onto `root_dir` and normalizes — with `root_dir` = `/` that is the absolute path itself; on Windows the native `C:\…` path is a single part and joining an absolute drive path onto the root replaces it, so any drive works (forward slashes would give a drive-relative `D:x`). jupyter silently walks up to `root_dir` when the directory doesn't exist, so Halo checks it first (400).
- **Kernel ops / channels** only for ids in Halo's in-process Map (unknown → 404, also when jupyter itself started it). Upstream 404 (culled) drops the id. A kernel jupyter shuts down on its own (idle cull) does **not** close its channels sockets — the only sign is an iopub `shutdown_reply` with `content.restart: false` (a restart sends the same frame with `restart: true`, and the socket keeps working across it); the proxy watches for that frame, drops the id and closes the client sockets 1000. A kernel that dies in a cell (`exit()`, a crash) is auto-restarted by jupyter: `status: restarting` → `starting`, same id, socket stays. Channels: WS `/api/jupyter/channels?kernel=<id>[&session_id=<s>]` → `ws://127.0.0.1:<port>/api/kernels/<id>/channels[?session_id=<s>]` (`session_id` `^[\w-]{1,128}$`, else 400; forwarded since 1.6.3 so jupyter's per-session buffering works, see Lifecycle), frames piped both ways as-is (text and binary), frames sent before the upstream handshake are queued. No subprotocol is offered upstream or accepted from the client, so jupyter speaks the **legacy JSON protocol** (every message a text frame carrying `channel`, `header`, `parent_header`, `metadata`, `content`, `buffers` go as binary frames). The proxy pings the client every 20 s (keepalive through reverse proxies; 2 missed pongs = dead).
- **Lifecycle**: a kernel with no client socket for **60 s** is DELETEd upstream (tab closed; the grace rides out a reload / reconnect, which cancels it; a kernel nobody ever connects to gets the same grace). **Reload**: since ipynb 2.0.1 the extension sends no `DELETE` on `pagehide` (it can't tell a reload from a close; 2.0.0's unload `DELETE` killed the kernel on every reload) — it closes the socket and stores `{id, name, session, run: {msgId, cellId, index, source, count, outputs}}` in `sessionStorage` (`halo-ipynb-kernel:<projectId>:<path>`, per browser tab, claimed once by the next page of that notebook). The next page reconnects with the same id and `session_id`; a handshake that fails (id gone after the grace, server restarted) falls back to a fresh kernel on the next run. jupyter_server (verified 2.21.1) buffers a disconnected session's messages and replays them to a socket that reconnects with the same `session_id` — output printed during the reload and the cell's `execute_reply` — and the proxy only reaches that buffer by forwarding `session_id` (1.6.2 doesn't: output in the gap is lost, live output still streams, and the shell `kernel_info_request` the extension sends on reattach, queued behind the running cell, still marks it done). jupyter sends no `status` to a new socket while the kernel is busy (its connect nudge skips busy kernels), so the extension sets the badge from what it stored (no route reads a kernel's state). The extension still `DELETE`s the old kernel when the user picks another kernelspec. jupyter culls kernels idle for 1 h even while connected, and exits itself after 10 min with no kernels. Halo's graceful shutdown POSTs upstream `/api/shutdown` (stops every kernel, then exits; works on Windows too) and SIGKILLs after 5 s; a `process.on('exit')` hook kills the child on other exits. If Halo dies hard, the orphaned server goes on its own: its kernels are culled after 1 h idle, then it exits 10 min later.
- Logs: `[Jupyter] server <version> ready on 127.0.0.1:<port>`, `kernel <id> (<name>) started in <dir>`, `no client for 60s, shutting it down`, `server exited (…); dropping N kernel(s)`.

### Extension skills

An extension can ship agent skills next to its viewer: `~/.halo/global/extensions/<extId>/skills/<id>/` (`SKILL.md` + resource files + optional `config.yaml`, the ordinary skill layout). Discovery is by directory; the manifest has no skills field. `packages/server/src/agents/skill-sources.ts` is the one resolver: every skill reader goes through `listSkillDirs` / `skillSourceDir`. That covers session build / `activate_skill`, slash commands, the `/skill` verbs, `GET /skills`, Settings → Skills and evo's listing.

- **Which folders count**: only switched-on extensions (`.state.json`, read from disk like everything here — a switched-off extension's skills vanish from every reader at once and return when it is switched on; `extensionSkillIds` lists them so their settings aren't orphaned meanwhile) whose manifest passes the registry's own validator (`readExtensionDir`, verdict and entry path cached per manifest mtime, the entry file re-checked on every scan; an extension with no `skills/` subdirs is skipped without reading its manifest). A skill id must match `^[\w-]+$` and equal `<extId>` or start with `<extId>-`; anything else is ignored with one `[Skills] extension "<extId>": ignoring skills/<id> …` warning per manifest version, not per scan. If two extensions claim one id (`foo`'s `foo-bar` vs extension `foo-bar`), the lower extension id keeps it. Manifest `platforms` is not applied: it only decides where the viewer is offered, and an extension's skills load on every platform.
- **Precedence**: workspace > global > extension. A higher source with the same id wholly overrides (the whole folder, no per-file fallback); the shadowed extension copy is still listed with `overridden: true`. To customise an extension skill, copy its folder into `~/.halo/global/skills/<id>/` or `<workspace>/.halo/skills/<id>/`.
- **Scope `extension`, read-only**: `GET /skills` returns them with `scope: 'extension'` and `extId`. `POST` / `DELETE /skills` with that scope answer 403, so they never fall through to a same-id global skill. `/skill delete` refuses them, and evo neither lists nor patches them. The admin shows them in a Skills → **Extensions** section, rendered as a read-only file view with no editor, create or delete, and the subtitle "from extension X".
- **Not auto-enabled**: an agent uses one only when its `skills:` lists the id (ticked in the agent form like any skill). An id whose extension is gone shows the usual "not installed" hint.
- **Disable**: the per-workspace toggle still works and is stored in `disabled_items` as `extension:<id>` (disabling is a workspace setting, not a write into the extension). `loadSkillMetadata` skips it.
- **Settings**: a `config.yaml` surfaces in Settings → Skills under the skill's own `<id>` namespace. Extension sections are laid down first, so a same-id global or workspace skill's section replaces them.
- **Read from disk**: the server, CLI / TUI and cron children all scan the extensions root on every read, never the in-memory registry, so every process sees the same set. In the admin, the `extension:changed` frame also bumps the skill bus, so the Skills sidebar and the agent form's skill picker refetch. Uninstalling removes the skills at once (next read finds no folder, no restart). The watcher is non-recursive, so editing files inside an installed extension's `skills/` pushes nothing. Reinstalling the extension is the way to publish a change.
- **Sandbox**: `~/.halo/global/extensions/**` is outside the sandbox hidden lists, so workspace- and readonly-access sessions can read the skill's resources, and a workspace-access `shell_exec` can run its scripts. `activate_skill` names the skill's absolute directory in its resources header, so the agent knows where they are.

### Extension docs

An extension documents itself; nothing it ships is injected into prompts or INDEX (per-turn tokens, and INDEX has a 12K-character budget).

- **Agent-facing instructions** → an extension skill (above). Opt-in per agent like any skill; an install never enables one by itself.
- **Human-facing docs** → `README.md` at the extension root (every halo-hub extension has one), plus `DESIGN.md` for internals. They ship in the zip and sit at `~/.halo/global/extensions/<id>/` once installed.
- **How agents find them** → the built-in `halo` skill (Platform Documentation, since `TEMPLATE_VERSION` 104) tells the agent to `file_read` that README when asked about an installed extension. The core repo's docs cover only what the core implements (protocol, capabilities, server proxies), not a hub extension's behavior.

## `extension` skill and halo-hub

Built-in skill `templates/skills/extension/` (in `BUILTIN_SKILL_IDS`; `TEMPLATE_VERSION` bumped to 69 in the same change): object command `/extension install|list|remove|models` (`models` = model provider configs, see the end of this section), `requiresAccess: full`. The built-in `default` agent lists it in `skills:` (since `TEMPLATE_VERSION` 81), so `/extension` shows in the command popup wherever the default agent is the built-in one. The payload reaches the body as `$ARGUMENTS`; when it names a source the agent installs right away without confirming, and it mentions the hub only when asked what exists or when an install fails. Everything goes through `templates/ext.sh` (curl + unzip + node; no `gh`, no git). `ext.sh install <id|zip|url>`: a zip path / URL is used as given, an id is fetched from the hub (below); then the same pre-check + six-step atomic replace as the server. It never talks to the server — the watcher picks the rename up within ~300 ms. The `halo` skill has a one-line pointer.

**Hub resolution (`install <id>`, since `TEMPLATE_VERSION` 108).** An id is read through the same [update.json protocol](#updates-updatejson) as the admin's update check — no release API, no platform detection, no git. `SKILL.md` runs `HALO_HUB_BASE='{{params.hub_base}}' HALO_HUB_REPO='{{params.hub_repo}}' bash EXT install <id>`; `hub_base()` takes the skill's `hub_base` param as given (trailing `/` dropped), else derives the GitHub raw `extensions/` directory on `main` from `hub_repo` (`https://raw.githubusercontent.com/<owner>/<repo>/main/extensions`; `hub_url` normalization: empty / unsubstituted `{{…}}` = `https://github.com/turmind/halo-hub`, `owner/repo` = GitHub), else nothing — a non-GitHub `hub_repo` with no `hub_base` stops with "no hub_base set …". The logic is self-contained `hub_*` functions and `ext.sh` is source-able (sourcing only defines them), so a later skill / workspace installer can reuse it.

- `hub_fetch_update`: `hub_base` must be https; every curl runs `--proto =https --proto-redir =https --max-redirs 5`. `<hub_base>/<id>/update.json` with `--max-time 10 --max-filesize 65536`, parsed by a node one-off with the server's rules (id, strict semver `version`, `url` resolved against the final redirected URL and https, 64-hex `sha256`, optional semver `minHalo`).
- `minHalo` → `hub_check_min_halo`: `${HALO_CLI:-halo} --version` with the build sha / `-dirty` dropped (the server's `haloBaseVersion` rule) and a semver compare; below → refuse with `<id> <ver> needs Halo X (this is Y) — upgrade Halo first: halo upgrade && halo server restart`; no readable version (no `halo` command, desktop, dev build) → a warning, and the install goes on.
- The zip: `--max-filesize 104857600 --connect-timeout 10 --max-time 600 --speed-limit 1024 --speed-time 30` (100 MB, 10 min, cut after 30 s under 1 KB/s); its sha256 must equal update.json's (`sha256 mismatch …`), and after unpacking the manifest id and version must equal update.json's (`manifest version … does not match update.json …`). Then the usual pre-check + atomic replace.
- curl uses the system CA store (`CURL_CA_BUNDLE` for a private CA); no token is sent anywhere on this path. Failures print a hint the skill relays (`no update.json for <id> at …` → wrong id or `hub_base`).
- Removed: the GitHub / Gitea / Forgejo / GitLab release-API pick and git tag mode for extensions. `hub_platform` / `hub_fetch_release` remain for `models` only (below).

The hub repo keeps one directory per extension (`glb` / `ipynb` commit their vendored deps, `fetch-deps.sh` only refreshes them; `drawio` / `excalidraw` gitignore their build output and commit only the inputs), `scripts/pack.mjs extensions/<id>` → `dist/<id>-<version>.zip` with contents at the zip root (maintenance scripts and build inputs excluded; `pack.mjs` hand-mirrors the `registry.ts` manifest rules, and `packages/server/test/extension-manifest-rules-drift.test.ts` pins a hash of those rules and fails with a pointer to the hub copy when they change), and one release per tag `<id>-v<version>` carrying the zip; `pack.mjs` also writes `dist/<id>-<version>.update.json` (absolute release-download `url`, `sha256` of that zip, `minHalo` inherited from the committed copy), which is copied to `extensions/<id>/update.json` and committed once the release exists — that commit is what publishes the version to `install <id>` and the update check. Skills and workspaces in the same repo are tagged `skill-<id>-v<ver>` / `ws-<id>-v<ver>`; nothing installs them yet. Catalog — nine extensions, versions as named by each committed `extensions/<id>/update.json` (halo-hub `2f930ac`, every one released as `<id>-v<version>`):

## On / off

A switch in Settings → Extensions makes an installed extension act as not installed while keeping its files and its settings values. Before it, uninstalling was the only way to stop an extension, and that threw both away.

- **State**: `~/.halo/global/extensions/.state.json`, `{ "<id>": { "disabled": true } }`; an id without an entry is on. The file sits beside the extension dirs, not inside one, so an update (which swaps `<id>/`) keeps the switch. As a dot-named direct child of the root, its atomic rename trips the watcher (→ `extension:changed` to every admin), while the scanner, `ext.sh list` and skill-sources skip it. `extensions/state.ts` is the only reader / writer in the server (`disabledExtensionIds` / `setExtensionDisabled` / `forgetExtension`). Writes go through `init.ts` `writeFileAtomic`; reads are cached by inode + mtime + size, so the server, CLI / TUI and cron children see the same switch without sharing memory. A file that isn't a JSON object reads as all-on (one warning per change) and is never overwritten: a switch then answers 500 until the file is fixed or deleted.
- **Lifecycle**: a fresh install (no `<id>/` before) drops a leftover entry, so it starts on (`install.ts`, `ext.sh` `state_forget`). An update keeps the entry. Uninstall (route and `ext.sh remove`) drops it; a failed write there only warns, because the directory is already gone.
- **Switch**: `PATCH /api/extensions/:id { enabled }` sets the target state; a repeat writes and pushes nothing. Error rows have no switch (404).
- **What off means**: the snapshot lists the extension under `disabled`. Everything that *offers* an extension reads `extensions` / `getExtension` and skips it: preview resolution and Open with, activity-bar and chat-bar entries, its shipped skills (skill-sources), its settings section, the Transcribe / STT handshakes (403) and the STT model reconcile. What *serves* an already-open tab uses `getInstalledExtension`, so assets keep loading and a dirty tab can still save (banner "This extension has been turned off. Save your changes, then close the tab."). Its settings values stay, and `extensionOffNamespaces` keeps them out of Orphans. Settings → Extensions is the only list that shows an off extension; the fallback page names it for its suffix.
- **Older servers**: the admin's `setExtensionsSnapshot` defaults `disabled` to `[]`, since a server from before the switch sends none.

## Updates (update.json)

Halo itself: notify only. An extension: one click. Code: `packages/server/src/updates/` (`update-json.ts` pure rules, `https-get.ts` the HTTP client, `extension-fetch.ts`, `core-check.ts`, `extension-check.ts`) + `routes/updates.ts` + the update route in `routes/extensions.ts`; wire types in `packages/core/src/protocol/update-types.ts`.

**update.json** — one small file per extension, read with a plain HTTPS GET from wherever it is hosted (git raw, S3, CDN, an intranet web server; no platform API, no paging):

```json
{ "id": "glb", "version": "1.2.0", "url": "glb-1.2.0.zip", "sha256": "<64 hex>", "minHalo": "2.1.0" }
```

- `id` must equal the extension's. `version` is strict semver `x.y.z[-pre]` (the manifest rule: no `v`, no `+build`). `url` is required, absolute or relative; a relative one resolves against the URL the file was finally read from (after redirects) and must come out https. `sha256` is 64 hex in any case, lower-cased. `minHalo` is optional semver. Unknown fields are ignored so the format can grow.
- **Where**: manifest `source` when set, else `<hub_base>/<id>/update.json`. `hub_base` is the extension skill's param (Settings → Skills → extension). Empty means it is derived from `hub_repo` for a GitHub hub (`https://raw.githubusercontent.com/<owner>/<repo>/main/extensions`; empty `hub_repo` = turmind/halo-hub). A non-GitHub `hub_repo` with no `hub_base` gives `no-source`. Hub extensions carry no `source`, so a mirror only changes `hub_base`; a third-party extension hosted elsewhere sets `source`. To move a source, the old update.json points at a version whose manifest carries the new `source`.
- **Verdict** (`judgeUpdate`): `semver.gt(update.version, installed)` → `available`. The same or an older version → `current`, so a downgrade is never offered. Newer, but `minHalo` above this Halo's base version (`haloBaseVersion`: `HALO_VERSION` minus `-<sha>` and `-dirty`) → `needs-halo`, with no Update button. A dev build (no base version) is not held back by `minHalo`.
- **Read failures**: `not-found` (404 / 410), `invalid` (not JSON, over 64 KB, a wrong field or id), `refused` (a non-https URL, redirects included), `unreachable` (network error, timeout, any other non-2xx); plus `no-source`, and `unknown` before the first check.

**Fetching** (`https-get.ts`) — the one HTTP client for npm, update.json and the zip. https only, with every redirect hop re-checked, ≤ 5 redirects. `maxBytes` is enforced by Content-Length, then while streaming. One deadline covers the whole call, redirects included, plus an optional idle timeout. Redirect and non-2xx bodies are destroyed unread. update.json: 64 KB, 10 s. Zip: `MAX_ZIP_BYTES` (100 MB, the upload cap), 10 min in total, aborted after 30 s without a byte. No proxy support (node:https ignores `HTTPS_PROXY`, like every server-side fetch in Halo). A private CA needs `NODE_EXTRA_CA_CERTS`. Where GitHub is slow (mainland China), point `hub_base` at a mirror.

**Trust boundary.** None of these URLs (`source`, `hub_base`, the package URL) goes through the A2A URL policy (`a2a/url-policy`). Intranet https, S3 and CDN sources must work; the instance-metadata endpoint is http-only, which https-only already excludes; extensions are installed by an admin; and a response is only ever parsed as a strict update.json, never echoed back. What is checked: https, size, time and redirects; then the zip's sha256 against update.json, and the unpacked manifest's id + version against update.json (`installExtensionZip(zip, id, version)`); then the usual pre-check and atomic replace. The sha256 ties the zip to its update.json, not to a publisher: whoever controls the update.json controls the package, the same trust as installing that zip by hand.

**Halo itself** (`core-check.ts`): the npm dist-tags `latest` of `@turmind/halo` (~40 bytes), from `npm_config_registry` when it is https, else registry.npmjs.org. `state` is `current` / `available` (`semver.gt(latest, base)`) / `error` / `dev` (no base version, never checked) / `unknown`. Upgrading stays `halo upgrade && halo server restart`, run by the operator.

**Cadence** (each scope on its own). No timer anywhere. `GET /api/updates?scope=core|extensions` answers from the in-memory cache at once, and starts a check only when there is no result or it is ≥ 24 h old. `POST /api/updates/check {scope}` forces one unless the last finished < 60 s ago. One check runs per scope at a time; a started one reports `checking: true`, and its result is pushed as `updates:changed {scope, status}` to every admin socket. Failures (404 included) are cached like successes, so an offline server tries once a day. A restart empties the cache, and the next Settings visit asks again. The extensions scope reads every installed extension, on and off, 4 at a time, and caches the raw update.json result per id. After a watcher broadcast (install, update, remove, switch), `rejudgeExtensionUpdates` re-judges against the new snapshot and pushes only if the status changed, with no network. Behind the admin cookie, not on the public `/api/health`; not mounted in AgentCore mode.

**One-click update** (`POST /api/extensions/:id/update`). No body. The server takes the extension with `getInstalledExtension` (on or off), re-reads its update.json now (never the cached copy, nothing from the client), and goes on only on `available`: download → sha256 → `installExtensionZip(zip, id, version)` → `rescanAndBroadcast()`. The on / off state is outside `<id>/`, so an off extension stays off. One update per id runs at a time (an in-process set; a restart mid-update leaves only dot-named staging dirs, which the scanner skips). Codes: 400 bad id; 404 not installed; 409 one already running, or the verdict is `current` / `needs-halo` (`{ error, status }`); 502 the source or its package is at fault — read failed or no source (`{ error, status }`), download or sha256 failure, or an `ExtensionInstallError` such as an id / version mismatch; 500 anything else. The fresh read replaces the cache entry, so the re-judge after the install already counts the new version as current.

**Admin.** Settings → Extensions shows the verdicts and the Update button (see [MRU, keep-alive, upgrade, uninstall](#mru-keep-alive-upgrade-uninstall)); an open tab picks the new version up like any upgrade. The Settings sidebar foot (`core-update.tsx`) shows "Halo v<version>" + **Check for updates**, then one of: `Up to date (X)`; `New version X` with `halo upgrade && halo server restart` (copy button), "Under a systemd system unit, use sudo — see the deploy guide." and a Release notes link (`github.com/turmind/halo-agent/releases/tag/vX`); in the desktop app only "Download the new installer" (the releases page); for a dev build "Source build — not checked" and no button; an error as one grey line. No badge anywhere, and nothing is checked until Settings is opened. Both views subscribe to `updates:changed`; no polling.

## Extension capability boundary

An extension **can**: receive one file's bytes and metadata; render in its own iframe; load static assets from its own directory via the path token; report `error`; receive `theme` and `lang`; with `save`, report `dirty` and hand back bytes for the host to write to **that same file**, and (on `init.export` hosts) hand back export bytes the host writes as a **new sibling file** after an overwrite confirm; with `bundle`, read / write / append / list / stat **inside its bundle directory** via `fs`; with `fs-read`, **read** (read / stat / list) any file in the workspace or on the machine outside the sandbox hidden lists, and ask the user to pick one; with `media`, use the microphone and screen capture; with `transcribe`, stream audio to the server's transcription proxy (results only — credentials stay server-side); with `stt-local`, stream audio to the server's on-device speech-to-text WS (`/api/stt/stream`); from a chat-bar panel, `insert-text` into the chat draft at the caret (never send) and, by reporting `busy`, finish its work before a user close unmounts it (35 s at most).

An extension **cannot** (sandbox + protocol): open popups, downloads, forms or navigate the top window; use camera / autoplay, or mic / screen capture without `media` (`allow=""`); add admin UI beyond one activity-bar entry and one chat-bar button declared in its manifest (`activity` / `chatbar` — see [Activity-bar entries](#activity-bar-entries), [Chat-bar entries](#chat-bar-entries)): no other toolbar buttons, commands or sidebars; send a chat message; talk to other iframes. The **protocol** gives it no way to write any workspace file except the open one (or inside its bundle directory), and no way to read others without `fs-read`. Since the host grants `allow-same-origin` (see Host), the sandbox no longer isolates it from the admin's origin: a hostile extension *could* script `parent.document` or call the cookie-authed `/api/*` (measured: `fetch('/api/extensions')` from inside → 200). That is the accepted trust model — installing an extension is like installing a skill — not a gap to patch per route. **Outbound network is not blocked** — no CSP is injected, so `fetch('https://…')` works where the remote allows CORS; trust model is "code the user chose to install" (same as a skill), and hub policy is offline-capable extensions. A hard block would be one `Content-Security-Policy` header on the asset route, no protocol change.

Adding a capability: (1) extend `ExtensionCapability` + the `CAPABILITIES` whitelist in `registry.ts`; (2) add the frame type in `extension-frames.ts`; (3) gate it in `extension-host-logic.ts` (undeclared → ignore + warn, like `save`); (4) if it needs the server (e.g. reading a sibling file), the **host** calls `/api/files/*` — an extension never touches the API directly. Install, scan, watcher and registry stay untouched.

## Deviations from the original design

1. **Install / delete are not full-access-only.** The admin cookie carries no access level, so list / install / delete / token are all "any logged-in admin". Only the agent-side `extension` skill keeps `requiresAccess: full`.
2. **Ctrl/Cmd+S does nothing on an extension tab** — Monaco isn't mounted, so there's no global shortcut. The toolbar Save button is the only trigger.
3. **No banner for an external change while dirty.** The host keeps the local edits silently and relies on the 409 (with the Overwrite confirm) on the next save.
4. **Conflict UI is chained `confirmAction`s**, not a dedicated overwrite / discard / cancel dialog (see Dirty, save, conflict).
5. **Uninstalling under a dirty tab** keeps the iframe alive with a banner — no confirm. A non-dirty tab shows the fallback page.
6. **Tests are not co-located**: `packages/admin/test/{extension-host-logic,extension-token,preview-registry,extension-activity,extension-chatbar,extensions-view}.test.ts`, `packages/server/test/{extensions-registry,extensions-install,extensions-routes,extensions-state,extensions-update-route,files-raw,extension-manifest-rules-drift,extension-hub,show-cookie-auth,update-json,updates-core,updates-extensions,updates-https,updates-routes}.test.ts`.
7. **`allow-same-origin` is granted** (design and first cut withheld it). Required for deployments behind a cookie-auth proxy; see Host and the capability boundary.
8. Smaller code-over-design points: the id regex is `ID_RE` (not `isSafeIdSegment`); staging dir is `.tmp-unpack-<rand>` (the id isn't known before unpacking); `snapshotKey` includes `installedAt`, so reinstalling the same version still broadcasts.

## Known limitations

- `file:changed` reaches an extension tab only after the admin sent a WS `subscribe` (it does when a session is selected). Opening a workspace without picking a session attaches no watcher, so an open viewer won't auto-refresh. Pre-existing behavior, not introduced here.
- `PUT /files/raw`'s `expectMtime` must be the float `modifiedAt` from `GET /files/stat` (compared rounded); an integer-seconds × 1000 value 409s. The route is stat-then-write, not atomic.
- Install is `.zip` upload, `ext.sh install` (a zip path / URL, or an id via update.json) or the one-click update only: no marketplace, no online recommendations (the fallback page only links to the configured hub — `hub_repo` read from the settings schema, default turmind/halo-hub; a local-path / ssh hub is shown as plain text), no workspace-level install, no persisted "open with" choice, no backup of unsaved edits (MRU pinning is the only protection).
- No credentials on the update.json path: neither `install <id>` nor the server's check / update sends a token, so a private hub needs an update.json host that answers without one (an intranet server, a presigned or public S3 / CDN URL). Hub tokens go to the `models` release API only.
- No proxy for the server-side checks and updates (node:https ignores `HTTPS_PROXY`); `ext.sh` curl honors the usual proxy variables. A server that reaches the internet only through a proxy shows `unreachable` — use `hub_base` / `source` on a reachable host, or install the zip by hand.
